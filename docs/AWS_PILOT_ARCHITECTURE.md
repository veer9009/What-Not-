# Proposed five-user AWS pilot

Prepared 15 November 2026. **Preparation only; deployment remains NO-GO.** No AWS account inspection, resource creation, network change, production migration, credential change or local data transfer was performed. The owner has not selected a region, domain, budget, machine architecture or recovery objectives. This proposal does not authorize those actions.

## Smallest practical design

Use one Ubuntu **24.04 LTS** EC2 instance, initially 2 vCPU / 2 GiB RAM, encrypted 30 GiB gp3 EBS, Nginx serving the built SPA and proxying same-origin `/api/v1` to FastAPI on **127.0.0.1:8000**. Run Python under a dedicated non-login Unix account and systemd; no Docker. Start with one Uvicorn process and bounded worker timers; measure memory, connection use and burst credits before changing capacity. Build frontend artifacts away from the small production host. PostgreSQL 17 on the same host listens only on **127.0.0.1:5432**, uses SCRAM authentication and separate runtime/migration/backup roles. No port 5432 or 8000 is allowed through the security group or host firewall.

This is the cost minimum, with a **shared host, disk, AZ and compromise failure domain** for app and database. An instance failure takes the whole pilot down; an attacker with host administration may access both DB and runtime secrets. EBS encryption does not protect against that attacker. Off-host backups and a measured rebuild/restore are mandatory. This proposal assumes five users can accept maintenance and recovery downtime; owner acceptance is pending.

**Recommended upgrade:** private RDS PostgreSQL (initially Single-AZ, subject to measured sizing), encrypted storage, automated backups/PITR, deletion protection and an explicit final-snapshot policy. Keep the EC2 application host. Use a DB subnet group with private subnets in at least two AZs, no public accessibility, and DB SG TCP 5432 **only from the app SG**. Single-AZ RDS separates the database from host loss but is not highly available; Multi-AZ adds standby/failover at additional cost. Always connect using the real RDS DNS endpoint with `sslmode=verify-full` and a readable, maintained AWS RDS CA bundle via `sslrootcert`; never use `require`, an IP address, disabled certificate checks or a public DB as a workaround. See [AWS RDS VPC guidance](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_VPC.WorkingWithRDSInstanceinaVPC.html).

## ARM or x86

**Production runtime gate:** do not copy the local Python 3.10.11 environment. Upstream Python 3.10 reached end of life on 1 October 2026 ([Python support table](https://devguide.python.org/versions/)). Use the maintained Ubuntu 24.04 Python 3.12 packages and security updates, then verify the pinned requirements and application on that runtime; Ubuntu documents [24.04's Python 3.12 availability](https://ubuntu.com/developers/docs/reference/availability/python/). Python 3.12 compatibility, native wheels and Linux/ARM behavior remain NOT VERIFIED locally. Do not change the Windows recovery environment merely to obtain production evidence.

`t4g.small` is ARM64/Graviton2 with 2 vCPU / 2 GiB; `t3a.small` or `t3.small` is the x86 alternative. Select the matching official Ubuntu AMI architecture. Python code is portable, but this repository's successful local evidence is Windows/Python 3.10.11, **not Linux ARM certification**. `psycopg[binary]`, bcrypt, argon2-cffi and pydantic-core include native components. Before choosing ARM, install the exact pinned requirements in a disposable ARM environment using the selected Ubuntu Python version, run import/non-persistence/persistence checks on a disposable PostgreSQL DB, and smoke-test the built app. Confirm wheels exist or review a reproducible compiler/library build. Do not copy Windows `.venv`, x86 wheels or native Node modules. Choose x86 if compatibility cannot be demonstrated; x86/Linux and Ubuntu Python-version verification is still required. CPU burst charges/throttling and password-hash memory costs need load observation. [AWS instance specifications](https://docs.aws.amazon.com/ec2/latest/instancetypes/gp.html) document the hardware, not application compatibility.

## Network, host and identity controls

| Control | Proposed configuration and release evidence |
| --- | --- |
| VPC/routes | Dedicated small VPC; one public app subnet with an internet gateway for minimum-cost direct hosting. No NAT gateway, ALB or bastion in the minimum design. Add two private DB subnets for RDS. Record actual CIDRs/AZs/routes before approval; none are selected here. |
| Ingress/perimeter | HTTPS 443 only from the five participants' approved stable source CIDRs as the minimum gate covering **all** static/API/docs/listing paths. The application five-email allowlist alone leaves public browse accessible. Dynamic/mobile IP users require a separately reviewed identity access gateway/VPN design and its cost before broadening ingress. Do not use CORS as a perimeter. No inbound SSH. |
| HTTP/certificates | Prefer DNS-01 certificate issuance, allowing port 80 to remain closed. A future HTTP-01 choice must explicitly review port 80 challenge exposure and redirect rules. Nginx serves a valid public certificate for the approved hostname; renewal and expiry alert must be demonstrated. ACME DNS credentials must be narrowly scoped to the challenge zone. |
| DNS/address | One Elastic IP gives stable DNS A-record routing and recovery reassociation; it is chargeable even when idle. Use existing DNS if available; Route 53 hosted zone is optional. Domain registration is additional. Never point DNS before certificate/perimeter/smoke approval. |
| Administration | MFA/federated operator identity; no root-account daily use, no long-lived AWS keys on EC2. SSM Agent and scoped instance profile; Session Manager over outbound HTTPS with logged operator access and reviewed sudo permissions. Restrict who can start sessions/pass roles/run commands; the app user cannot administer the host. [SSM setup](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-getting-started.html). |
| IAM | Instance role can read only its runtime secret ARN, publish only its log streams/metric namespace, and upload only its backup prefix with necessary KMS permission. No IAM administration, database provisioning, broad `s3:*`, secret write or backup deletion. Operators/recovery role separately handle restore downloads and retention administration. SSM's baseline managed policy should be reviewed alongside narrower application policies. No migration credential in the runtime secret. |
| Metadata/storage | Require IMDSv2 tokens and hop limit 1 for this host deployment; restrict the app user's metadata access where feasible. Encrypt root/data EBS and snapshots; document KMS key recovery access. No public snapshots. Host firewall mirrors SG restrictions; unattended security patches, reboot window and disk/inode monitoring. [IMDS options](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-instance-metadata-options.html). |
| Secrets | Dedicated production DB/JWT/SMTP secrets supplied after separate authorization, never copied from local `.env`. Prefer Secrets Manager read by a privileged startup helper into a protected runtime file (`root:whatnot`, 0640; directory 0750 or stricter); application gets only runtime values. No secrets in Git, VITE variables, unit command lines, user-data, build logs or shell history. Document controlled rotation/restart and recovery access. File injection/helper behavior must be reviewed and tested; none is installed here. |
| App/proxy | Production DB required; remote DB verified TLS; explicit HTTPS CORS and trusted host; strong JWT key and exactly five admitted emails including admin; STARTTLS for enabled SMTP. Nginx same-origin `/api/v1`; Uvicorn trusts proxy headers only from loopback. Verify forged forwarding headers cannot evade quotas. Apply security headers, body/time limits and private/no-store API caching. |

## Monitoring and remaining gates

Propose 14-day redacted operational logs; no tokens, passwords, recipient/message bodies or exact addresses. Monitor EC2 status, disk/inodes, memory/swap, CPU/burst balance, PostgreSQL health/connections, HTTPS 5xx/latency, worker exit/missed runs, outbox failed/oldest age, latest successful **off-host** backup and certificate expiry. EC2 basic metrics do not include memory or filesystem occupancy: install/configure an agent or bounded publisher deliberately. Exercise alert delivery with synthetic events. `/health` is liveness; `/ready` checks schema/backlog and must remain inside the pilot perimeter.

Before deployment approval: owner selects account/region/domain/architecture/budget and accepts single-host failure risk or chooses RDS; resolves stable-IP perimeter feasibility; reviews IAM/SG/routes/OS/TLS/systemd templates; demonstrates Linux dependency compatibility and five-user workflows; approves SMTP and privacy policy; completes [backup and isolated restore rehearsal](PRODUCTION_BACKUP_RECOVERY.md); records target identity, secrets delivery, alert receipt, external port exposure and denied nonparticipant access. Local successful authentication recovery and passing tests are not AWS evidence.
